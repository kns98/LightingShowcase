# LightingShowcase v1

LightingShowcase is a Windows scene editor and command-line renderer with software raster, Vulkan raster, Vulkan compute, and CPU ray/path-tracing backends for `.lscene`, `.lsb`, `.prop.xml`, `.xml`, `.glb`, `.gltf`, `.fbx`, `.obj`, `.3ds`, `.ply`, and `.stl` files.

This file is the detailed technical reference for v1. `README.md` provides the project overview and quick-start instructions, while this file combines the applicable implementation notes that were previously stored across many Markdown files.

## v1 command-line workflow

The command-line renderer accepts a **local scene/model file**. Referenced textures and related assets are resolved from the scene's own directory tree, including filename relocation for scene files that contain an older absolute asset path. No scene packaging step is required.

```text
LightingShowcase.CommandLine render <scene> [render options]
LightingShowcase.CommandLine <scene> [render options]
LightingShowcase.CommandLine formats
LightingShowcase.CommandLine options
```

### Input and output

```text
--input <path>                 Local scene/model path; a positional path is also accepted.
--output <path>                PNG output path. Default: <scene-name>-render.png beside the scene.
```

### Renderer

```text
--renderer <name>              raster | raster-vulkan | vulkan | cpu
                               Default: vulkan. Raster modes require Windows.
```

- `raster`: software/CPU z-buffer rasterizer with shadow maps.
- `raster-vulkan`: Vulkan graphics-pipeline hardware rasterizer.
- `vulkan`: Vulkan compute BVH ray/path tracer.
- `cpu`: CPU ray/path tracer.

### Image quality

```text
--width <1-32768>              Output width. Default: 1920.
--height <1-32768>             Output height. Default: 1080.
--samples <1-4096>             CPU/Vulkan path samples. Ignored by raster modes. Default: 1.
--bounces <0-8>                CPU/Vulkan path bounces. Ignored by raster modes. Default: 2.
```

### Camera

```text
--camera-position <x,y,z>      Camera position. Default: automatically framed.
--camera-target <x,y,z>        Look-at target. Default: scene center.
--camera-up <x,y,z>            Up vector. Default: 0,1,0.
--fov <1-179>                  Vertical field of view in degrees. Default: 72.
```

### Lighting and tone

```text
--exposure <0.01-100>          Exposure before tone mapping. Default: 1.
--ambient <0-100>              Ambient-light multiplier. Default: 1.
--background-top <r,g,b>       Top linear RGB background. Default: 0.055,0.060,0.072.
--background-bottom <r,g,b>    Bottom linear RGB background. Default: 0.010,0.012,0.016.
--shadows <true|false>         Enable or disable cast shadows. Default: true.
--no-shadows                   Convenience switch equivalent to --shadows false.
```

The command-line renderer accepts `--renderer raster`, `--renderer raster-vulkan`, `--renderer vulkan`, or `--renderer cpu`. Vulkan compute remains the default for backward compatibility. All four rendering modes are available in both the Windows and portable command-line builds; the two Vulkan modes require a working Vulkan runtime and driver. Unknown options are rejected with an error, and `render --help` prints the complete option reference.

### Examples

```bash
LightingShowcase.CommandLine room.gltf --renderer raster --output room.png
LightingShowcase.CommandLine room.gltf --renderer raster-vulkan --output room-vulkan-raster.png
LightingShowcase.CommandLine render scenes/room.lscene --renderer vulkan --width 3840 --height 2160 --samples 64 --bounces 4
LightingShowcase.CommandLine model.obj --renderer cpu --samples 8 --fov 50 --exposure 1.25
```

## Asset resolution

For command-line rendering, the scene directory is the only configured asset root. The loader first honors an existing path, then resolves relative paths from the scene directory, and finally searches the local scene directory tree for the same filename. This supports ordinary folders without requiring an archive or generated package.

Recommended layout:

```text
project/
  room.gltf
  room.bin
  textures/
    wall.png
    floor.jpg
```

Run the renderer against `project/room.gltf`; keep its referenced files under `project/`.

## Former document: `ADDITIONAL_IMPORT_FORMATS.md`

### Additional import formats

This patch adds static mesh import for more widely available free 3D asset formats.

#### Supported import types

- `.obj` — existing Wavefront OBJ/MTL support, including UVs and texture references where present.
- `.stl` — new ASCII and binary STL support. STL does not carry UVs or textures, so the importer generates box-projection UVs for later texture application.
- `.ply` — ASCII, binary little-endian, and binary big-endian PLY support. The importer reads vertex positions and polygon faces, skips unsupported extra properties such as vertex color, triangulates n-gons, and generates box-projection UVs.
- `.3ds` — legacy Autodesk 3DS static mesh support with vertices, faces, UVs, diffuse material colors, and texture file references.

#### UI integration

The Open File and Insert Object dialogs include OBJ, STL, PLY, and 3DS model filters. Drag-and-drop also accepts `.obj`, `.stl`, `.ply`, `.3ds`, `.xml`, and `.prop.xml`.

#### Notes

GLB/GLTF and FBX are better handled through a library such as AssimpNet or SharpGLTF because those formats include complex scene/material/animation structures. This patch keeps the project dependency-free and avoids adding native importer binaries.

#### Supported export types

- `.prop.xml` / `.xml` — native scene format, preserving editor objects, lights, transforms, materials, and texture metadata.
- `.obj` — Wavefront OBJ plus companion `.mtl`, preserving diffuse colors, UVs, and texture references.
- `.stl` — binary or ASCII STL triangle geometry. STL does not support materials or UVs, so the export is geometry-only.
- `.ply` — binary little-endian or ASCII PLY with vertex positions and UVs. Material data is omitted because PLY material conventions are inconsistent and the current importer intentionally ignores PLY color/material extensions.
- `.3ds` — legacy Autodesk 3DS static meshes with UVs, diffuse colors, and texture file names. Large scenes are split into multiple object chunks to respect 3DS vertex/face limits.


## Former document: `BINARY_CLOSED_FILE_SAVE_FIX.md`

### Binary scene save closed-file fix

The version 3 binary scene writer previously used nested `using` declarations where
`DeflateStream` and the compressed-body `BinaryWriter` could close the underlying
`FileStream` before the header writer finished disposal.

That ordering can surface as:

> Cannot access a closed file

The save path now:

1. Writes and disposes the header writer before opening the compressed body.
2. Opens `DeflateStream` with `leaveOpen: true`.
3. Opens the body `BinaryWriter` with `leaveOpen: true`.
4. Flushes the body writer and lets `DeflateStream.Dispose()` finalize compressed bytes.
5. Lets the owning `FileStream` close last.

The loader was also adjusted so the decompression stream does not prematurely close the
base file stream while the outer owner is still active.


## Former document: `BINARY_SCENE_FORMAT.md`

### Lighting Showcase binary scene format

This patch adds a compact native scene format for normal project save/load:

- `.lscene` is now the default Save format.
- `.lsb` is accepted as an alternate extension.
- `.prop.xml` remains available for readable/manual editing.
- OBJ/STL/PLY/3DS remain export formats.

#### Why this exists

XML is useful for debugging and hand-editing, but it is expensive when a scene has many triangles because every coordinate and material value is serialized as text.

The binary scene format writes the same editor data in compact records:

- scene description
- editable lights, including enabled/disabled state
- object names
- object hierarchy
- transforms
- color overrides
- materials
- texture references
- semantic primitive records when detectable
- indexed object mesh fallback when geometry is not primitive-like

#### Primitive preservation

The saver tries to keep objects semantic before falling back to raw triangle records:

1. Built-in menu primitives such as sphere, cylinder, cone, torus, capsule, pyramid, triangular prism, and wedge are stored as primitive records.
2. Axis-aligned cuboid parts are stored as compact cuboid records.
3. Rectangular faces are stored as compact rectangle records.
4. Freeform/imported geometry is stored as binary mesh triangles.

For example, the coffee table should serialize as one object containing five compact cuboid geometry records: tabletop plus four legs.

#### UI behavior

Save now defaults to:

```text
Lighting Showcase Binary (*.lscene)
```

Use XML explicitly when you want a human-readable file:

```text
Prop XML (*.prop.xml)
```

Open and drag/drop now accept `.lscene` and `.lsb`.


## Former document: `BINARY_SCENE_OPTIMIZATIONS.md`

### Binary scene file optimizations

This version upgrades the native `.lscene` / `.lsb` format to version 3.

#### Why the previous binary file could be larger than OBJ

Version 2 removed repeated texture metadata, but it still wrote raw triangle data directly:

- every triangle stored three full vertices;
- every triangle stored three full UV coordinates;
- every triangle stored a full material record/reference payload;
- all numeric values were written as 64-bit doubles;
- the stream was uncompressed.

OBJ can look surprisingly efficient because it uses shared vertex tables (`v`, `vt`, `f`) instead of repeating every vertex for every triangle.

#### Version 3 changes

Version 3 keeps the native scene data, but writes it much more like an efficient mesh/project format:

1. **Compressed scene body**
   - File header remains plain: magic + version.
   - The scene body is written through `DeflateStream` using `CompressionLevel.SmallestSize`.

2. **Material table**
   - Materials are written once at the scene level.
   - Objects, primitives, and mesh faces reference materials by ID.

3. **Indexed mesh records**
   - Mesh fallback data now stores a per-mesh vertex/UV table.
   - Faces reference vertex/UV rows by compact integer indices.
   - This avoids repeating identical vertex and UV records on adjacent triangles.

4. **Single-precision mesh payload**
   - Indexed mesh vertex positions and UVs are stored as 32-bit floats.
   - Editor transforms, lights, primitive bounds, colors, and older compatibility readers still use the existing double-based path.

5. **Compact face indices**
   - Mesh face indices and material references use variable-length integer encoding.
   - Small scenes usually use one byte per index instead of four.

#### Compatibility

The loader still supports older version 1 and version 2 `.lscene` files.
Version 3 files require this updated loader because their scene body is compressed and uses material/index tables.

#### Expected effect

For imported OBJ-like mesh data, `.lscene` should now be much closer to OBJ size, and often smaller when repeated materials, repeated UVs, primitive objects, and compression are present.

For editor primitives such as cuboids, rectangles, and menu-created primitives, `.lscene` should remain much smaller than any triangle-only export format because those objects are preserved semantically where possible.


## Former document: `BINARY_TEXTURE_ID_TABLE.md`

### Binary Scene Texture ID Table

The native `.lscene` / `.lsb` binary scene format now writes textures once in a scene-level texture table.

#### Previous behavior

Each material record carried its own texture metadata.  If many triangles or parts shared the same texture, the same texture name, size, source path, and built-in checker flag could be repeated many times.

#### New behavior

Version 2 binary scene files use this structure:

```text
LSCN
version = 2
description
texture table
  texture 0
  texture 1
  ...
lights
objects
  materials reference textureId
```

Each material now stores only:

```text
color
emission
light id
texture id   // -1 means no texture
```

This makes heavily textured scenes smaller and easier to load because the loader resolves each unique texture only once.

#### Compatibility

The loader still reads version 1 `.lscene` files.  Version 1 material records are decoded using the old inline texture metadata layout.

New saves use version 2 automatically.

## Former document: `BUILT_IN_OBJECT_ROTATION_MATCH_FIX.md`

### Built-in Object Rotation Match Fix

The Helix live-preview transform now uses the same affine transform math as
`SceneObjectGroup.TransformPoint`, which is also the path consumed by the
raytracer.

Previously the preview used a WPF `Transform3DGroup` with separate X/Y/Z
`RotateTransform3D` children.  That can compose Euler rotations differently
from the scene graph, making asymmetric ready-made objects such as the built-in
Bed appear rotated differently in Helix than in the rendered output.

The fix builds a single `MatrixTransform3D` from the scene transform basis so
Helix preview, committed scene geometry, picking, and final render all use the
same rotation convention.


## Former document: `CANCELLATION_FIX.md`

### Cancellation fix

This patch removes user-visible `OperationCanceledException` breaks from the background raytracer.

Changes:

- `FrameRenderer.RenderProgressivePass` no longer uses `ParallelOptions.CancellationToken`.
- `FrameRenderer.RenderAccumulationPass` no longer uses `ParallelOptions.CancellationToken`.
- Parallel loops now check `cancellationToken.IsCancellationRequested`, call `loopState.Stop()`, and return normally.
- Background render orchestration in `LightingShowcaseForm` now checks cancellation explicitly instead of calling `ThrowIfCancellationRequested()`.

Reason:

Visual Studio can break on `OperationCanceledException` from a worker thread even when the task-level code catches it. For render cancellation this is expected control flow, so the renderer now treats cancellation as a normal early exit instead of an exception.

## Former document: `EXTERNAL_LIGHTING_FORMATS.md`

### External scene formats with lighting

This build adds external scene-format support for **glTF 2.0**:

- `.gltf` JSON glTF scene files
- `.glb` binary glTF scene files

Unlike OBJ/STL/PLY, glTF/GLB can carry scene structure and lighting. The importer/exporter uses the standard `KHR_lights_punctual` extension for point lights.

#### Import behavior

Opening or inserting `.gltf` / `.glb` now imports:

- triangle meshes
- node/object names
- node translation/rotation/scale transforms
- base material color
- emissive material factor
- UV coordinates where present
- point lights from `KHR_lights_punctual`

If a glTF/GLB file does not contain lights, the loader adds safe default preview lights so the model is still visible.

#### Export behavior

Exporting to `.gltf` or `.glb` writes:

- visible scene objects as glTF meshes
- object names as node and mesh names
- basic materials
- UV coordinates
- editable enabled scene lights as `KHR_lights_punctual` point lights

`.gltf` writes a JSON file plus a companion `.bin` file. `.glb` writes a single binary file.

#### Limits

The built-in loader intentionally supports a practical subset of glTF 2.0 so the project does not need a large third-party dependency. It does not yet import skinned animation, morph targets, cameras, image textures, or non-point lights. Directional and spot lights can be added later using the same extension path.

OBJ, STL, PLY, and most 3DS files should still be treated as geometry-first formats. Use glTF/GLB when you need an external file that can also round-trip lighting.


## Former document: `FAST_UNGROUP_OPTIMIZATION.md`

### Fast ungroup optimization

Ungroup used to split every local mesh directly into one object per triangle.
For large models that created thousands of `SceneObjectGroup` instances and made
selection/UI refresh very slow.

This patch changes ungroup to a staged, indexed algorithm:

1. Child groups are still promoted first.
2. Local mesh geometry is split into disconnected components using a quantized
   vertex map and disjoint-set union. This is O(n) over triangles rather than
   pairwise triangle comparison.
3. If the selected object is a single connected component, triangles are paired
   into rectangular face objects using a shared-edge hash map.
4. Very large connected meshes are first split into editable chunks, so the UI
   does not freeze from creating excessive face/triangle objects in one step.
5. Raw one-triangle groups remain the terminal primitive.

This keeps cuboids/table legs/tabletops intact on the first ungroup while making
large imported or generated meshes much faster to expand.

### Group rotate no scale/proportion change fix

#### Problem

After rectangle-selecting several objects, grouping them, and rotating the group, the selected objects could appear to change proportions or rotate awkwardly.

#### Cause

The Helix preview path could rebuild mesh vertices with the root group's rotation already baked into the geometry, then apply the same root transform again through `GeometryModel3D.Transform` during live preview. That made rotation look like scale/skew.

- Rotation paths explicitly preserve `group.Scale`.
- Compound group pivots are no longer recalculated during normal move/rotate/scale commits.

## Former document: `GROUP_ROTATE_PROPORTION_FIX.md`

### Group rotate proportion fix

#### Problem

After rectangle-selecting multiple objects, using **Group**, and then rotating the new group, some objects could appear stretched/skewed or have their proportions thrown off.

#### Cause

The group commit path baked transforms into geometry for every selected group, including recursive parent groups. For a compound group, the parent rotation/scale should remain on the parent node. - Parent `Position`, `Rotation`, and `Scale` are preserved as metadata.

- Parametric single objects still use their authored parameter path as before.
- Flattening is deferred to explicit destructive operations such as Ungroup.

2. Click **Group**.
3. Rotate the new group.
4. All child objects rotate together around the group pivot while preserving their individual proportions.

## Former document: `SIMPLIFY_NO_GAPS_FIX.md`

### Simplify No-Gaps Fix

The previous **Simplify selected** command used spatial representative-triangle
selection.  That was fast, but it removed individual faces, so closed objects
could turn into a surface with visible holes.

The simplifier now uses topology-conscious vertex clustering:

1. Nearby vertices are assigned to spatial cells.
2. Each cell becomes one averaged vertex.
3. Original faces are rebuilt using the clustered vertices.
4. Degenerate and duplicate faces are discarded.

This keeps neighboring faces stitched together much better because the command no
longer deletes random surface patches.  It is still a lightweight editor
simplifier, not a full CAD-grade quadric-error optimizer, so very aggressive
settings can still distort shapes.  Use larger **Keep %** values such as 50-80%
when visual fidelity matters.

## Former document: `VULKAN_BLACK_BUFFER_TILE_FIX.md`

### Vulkan black buffer tile fix

This build changes the Vulkan compute renderer to avoid one large brute-force dispatch for complex scenes.

The current Vulkan path is compute-based, not BLAS/TLAS Vulkan RT. It performs roughly:

```
pixels * triangles * ray-bounces/shadow-rays
```

Complex scenes at full resolution can cause the driver to return an all-black buffer without a managed exception. To make the failure easier to isolate and reduce watchdog pressure, the renderer now:

- keeps the shared Vulkan device alive,
- initializes the output buffer before dispatch,
- dispatches the compute shader in small row tiles,
- waits after each tile,
- logs tile progress to `%TEMP%\\LightingShowcase-vulkan-stage-log.txt`,
- passes tile offset/height through the constants buffer,
- sanitizes NaN/Infinity color values in the shader.

If a black buffer still appears, the stage log should now show whether the renderer completed every tile or stopped in a specific tile range.

## Former document: `VULKAN_CANCELLATION_CLEANUP_FIX.md`

### Vulkan cancellation and cleanup fix

This build changes the Vulkan compute path to make progressive rendering safer when bounces are enabled.

#### Changes

- Reuses one shared Veldrid Vulkan `GraphicsDevice` instead of creating/destroying a device for every progressive sample.
- Runs the isolated Vulkan device preflight only once per app session instead of once per sample.
- Adds cancellation checks before expensive Vulkan stages.
- Keeps per-sample GPU resources (`DeviceBuffer`, `Shader`, `ResourceLayout`, `ResourceSet`, `Pipeline`, `CommandList`) in `using` scopes so they are disposed on cancellation or failure.
- Disposes the shared Vulkan device on GPU failure so a bad/lost device is not reused.
- Disposes the shared Vulkan device during form cleanup.

The previous progressive Vulkan path recreated the Vulkan `GraphicsDevice` for every sample. With bounces enabled, the render loop repeatedly created and destroyed Vulkan/Veldrid device state. On some drivers this can fast-fail or crash before managed exceptions are produced.

The stage log should now show either:

```text
Create shared Veldrid Vulkan GraphicsDevice in main process
```

for the first sample, or:

```text
Reuse shared Veldrid Vulkan GraphicsDevice
```

for later progressive samples.

## Former document: `VULKAN_GPU_BLACK_BATCH_FIX.md`

### Vulkan GPU Black Batch Fix

#### Problem

The previous GPU performance patch made the Vulkan path batch multiple samples and allowed much taller row tiles. On heavy renders such as `899x672`, `7488` triangles, `8` bounces, and sample ranges like `57-64`, that created very large compute dispatches (`8 samples x 168 rows x 8 bounces`). Some Vulkan drivers can complete that workload by returning an all-black output buffer instead of a valid image.

#### Fix

- The Vulkan tile scheduler now includes `sampleCount` when choosing `tileRows`.
- Deep-bounce renders use smaller GPU sample batches:
  - `>= 6` bounces: 1-2 samples per batch depending on resolution.
  - `>= 3` bounces: 2-4 samples per batch depending on resolution.
- Per-dispatch workload is capped more conservatively while still keeping command-list batching to avoid a `WaitForIdle` after every tiny tile.
- The black-output detector now only rejects a truly empty Vulkan readback instead of rejecting any very dark-but-valid scene.

#### Expected behavior

For the reported scene, the Vulkan status should no longer show `samples=57-64, tileRows=168`. It should use a smaller sample range and much smaller tile row count for 8-bounce renders.

### Vulkan Raster Baked Texture Color Fix

This build addresses Vulkan Raster Preview showing textured glTF assets as white/gray outlines.

#### Root cause being tested

## Former document: `VULKAN_STALE_BATCH_AND_SUBMIT_FIX.md`

### Vulkan stale/black batch and bounded submit fix

This patch fixes the behavior where the Vulkan renderer would appear to work for a few samples, then stop visually improving while the reported render speed increased.

Root cause:

- The previous performance patch batched every row tile for a frame into one Vulkan command-list submission.
- `tileRows` limited the size of each dispatch, but it no longer limited the total GPU work submitted before `WaitForIdle`.
- On deep-bounce scenes this can trigger watchdog/driver failure modes where later batches return all-black or stale output quickly.
- The app only validated the final accumulated image, so a bad late batch could be counted as completed work.

Changes:

1. Bounded Vulkan command-list submissions
   - Row tiles are still batched, but only a small number of tiles are submitted per command list.
   - Deep path-tracing renders (`bounceCount >= 6`) use one tile per submit for stability.
   - Lighter scenes can still submit multiple tiles per command list.

2. Per-batch GPU output validation
   - Every Vulkan sample batch is analyzed before accumulation.
   - Invalid all-black batches are not counted as completed samples.
   - If a multi-sample batch fails, the renderer resets the shared Vulkan device and retries the same sample as a single-sample batch.
   - If the retry fails too, the explicit GPU backend reports a real Vulkan failure instead of silently accepting bad samples.

3. Safer high-bounce sample scheduling
   - For `bounceCount >= 6`, GPU sample batches are now one sample at a time.
   - This keeps each sample smaller and prevents false speedups caused by invalid fast-returning batches.

Expected result:

- Vulkan should no longer render correctly at first and then stop contributing useful samples.
- The render may be a little slower than the overly aggressive patch, but it should remain stable and honest.
- Stage logs now include bounded tile batch submissions, which makes it easier to diagnose driver sensitivity.

### Vulkan Triangle AABB Padding Fix

#### Problem

A lamp shade / cylinder mesh could render as if alternating triangle halves were missing in the Vulkan GPU renderer.

The CPU renderer pads each triangle AABB in `Aabb.Around()` by `1e-5`, which keeps thin or flat triangles from being rejected by the BVH bounds test before the actual ray/triangle intersection runs.

The Vulkan GPU BVH previously built exact float bounds for each triangle. - Added scale-aware conservative bounds padding in `VulkanSceneComputeRenderer.BuildGpuBvh()`.
- Added `ComputeGpuBoundsPad()` so the tolerance scales with imported model size.
- Relaxed the shader-side AABB slab comparison by a tiny epsilon.
- Added stage logging for the GPU BVH pad value.

- `Rendering/VulkanSceneComputeRenderer.cs`
- `Shaders/vulkan_scene_primary.comp`

## Linux Vulkan `libdl` compatibility

On Ubuntu installations where the Vulkan renderer fails during the isolated Veldrid preflight with:

```text
System.DllNotFoundException: Unable to load shared library 'libdl'
```

verify Vulkan first:

```bash
vulkaninfo --summary
```

Ubuntu normally provides `libdl.so.2`, while the Vulkan binding used by Veldrid may request `libdl.so`. Create a local compatibility link beside the Linux command-line executable:

```bash
cd ./LightingShowcase.CommandLine/bin/Release/net8.0

LIBDL="$(ldconfig -p | awk '/libdl\.so\.2/ {print $NF; exit}')"
test -n "$LIBDL" || {
    echo "libdl.so.2 was not found"
    exit 1
}

ln -sfn "$LIBDL" ./libdl.so
ls -l ./libdl.so
```

Use `bin/Debug/net8.0` for Debug builds or the applicable publish directory for published builds. The link is local to that output directory and must be recreated after cleaning or republishing.

If the isolated preflight reports only exit code `0x0000000A`, use one diagnostic run to reveal the underlying native exception:

```bash
LIGHTINGSHOWCASE_SKIP_VULKAN_PREFLIGHT=1 \
LIGHTINGSHOWCASE_VERBOSE_ERRORS=1 \
./LightingShowcase.CommandLine \
  --input "$HOME/Downloads/scene.glb" \
  --renderer vulkan \
  --output "$HOME/Downloads/out.png" \
  2>&1 | tee "$HOME/Downloads/lighting-vulkan-error.txt"
```

The preflight bypass is diagnostic only; the `libdl.so` compatibility link is the fix for the missing-library error.
